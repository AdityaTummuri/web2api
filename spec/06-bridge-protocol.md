# 06 — Bridge ⇄ Extension WebSocket Protocol (v1)

This is the contract between `bridge/web2api_bridge/hub.py` and
`extension/src/background/bridge-client.js` + `job-runner.js`. Both sides must implement it exactly.
Constants (message types, error codes, close codes) live in **one place per side** and must match:
`extension/src/shared/protocol.js` and `bridge/web2api_bridge/protocol.py`. A test on the bridge side
parses `protocol.js` with a regex to assert both lists are identical (`09-testing-strategy.md` §5).

---

## 1. Transport

* Endpoint: `ws://127.0.0.1:<port>/ws/extension` (default port 8787).
* Text frames only, each frame = one UTF-8 JSON object. No binary frames.
* Max frame size: 16 MiB (bridge: set uvicorn `ws_max_size=16 * 1024 * 1024`; snapshots can be ~2 MB).
* Exactly one JSON object per frame; no batching.

## 2. Envelope

Every frame has:

| Field | Type | Required | Meaning |
|---|---|---|---|
| `type` | string | yes | Message type (§3–§6). Upper snake case. |
| `ts` | integer | yes | Sender's `Date.now()` / `time.time_ns() // 1_000_000` in ms. Informational. |
| `jobId` | string | for `JOB_*` | `job_` + 26-char ULID or random base32. Generated by the **bridge**. |
| `requestId` | string | for request/response pairs that aren't jobs | `req_` + random. Generated by the requester; echoed in the reply. |

Unknown fields must be ignored (forward compatibility). Unknown `type` → reply
`ERROR { requestId?, code: "UNKNOWN_TYPE" }` and continue (never close the socket for this).

## 3. Connection lifecycle

### 3.1 Handshake

```
Extension                                   Bridge
   │  (WebSocket upgrade, Origin: chrome-extension://abc… / moz-extension://…)
   │ ─────────────────────────────────────────►│  check Host + Origin (08 §3.2) → reject = HTTP 403 before upgrade
   │                                           │  accept
   │ HELLO ───────────────────────────────────►│  must arrive within 5 s (else close 4408)
   │                                           │  check protocolVersion (major) → else close 4400
   │                                           │  check token (constant-time) → else close 4401
   │◄─────────────────────────────────── WELCOME│
   │ PROVIDERS_UPDATE ────────────────────────►│
   │           … normal operation …            │
```

`HELLO` (extension → bridge):
```json
{
  "type": "HELLO", "ts": 1760960000000,
  "protocolVersion": 1,
  "token": "<pairing token>",
  "instanceId": "inst_7Q2…",            // random, generated once per extension install, persisted in storage.local
  "extensionVersion": "0.1.0",
  "browser": { "name": "chrome", "version": "130.0.6723.58" },
  "capabilities": ["stream", "cancel", "config_override", "health_probe", "snapshot"]
}
```

`WELCOME` (bridge → extension):
```json
{
  "type": "WELCOME", "ts": 1760960000005,
  "protocolVersion": 1,
  "bridgeVersion": "0.1.0",
  "connectionId": "conn_3F…",
  "heartbeatSec": 20,
  "replacedConnection": false
}
```

**Duplicate instance:** if a connection with the same `instanceId` already exists (extension reloaded,
old socket not yet closed), the bridge closes the **old** one with code 4409 *after* sending `WELCOME`
to the new one and sets `replacedConnection: true`. Jobs that were running on the old connection are
failed with `EXTENSION_RESTARTED` (fixes L-05: the old socket's close handler must only clean up its own
connection object).

**Multiple different instances** (e.g. Chrome and Firefox both running the extension) are allowed;
the router chooses between them (`07-bridge-server-spec.md` §4).

### 3.2 Close codes

| Code | Sent by | Meaning | Extension behaviour |
|---|---|---|---|
| 1000 | either | Normal close | Reconnect with backoff (unless the extension is shutting down). |
| 4400 | bridge | Protocol version mismatch | Stop reconnecting; popup shows "Version mismatch: bridge vN, extension vM". |
| 4401 | bridge | Bad/missing token | Stop reconnecting; popup shows "Pairing token rejected". |
| 4403 | bridge | Origin not allowed (if detected after upgrade) | Stop reconnecting; show error. |
| 4408 | bridge | Handshake timeout | Reconnect with backoff. |
| 4409 | bridge | Replaced by a newer connection from the same instance | Do **not** reconnect from this socket (the newer socket is already connected). |
| 4500 | bridge | Bridge shutting down | Reconnect with backoff. |

### 3.3 Heartbeat

* Either side may send `PING { nonce }`; the other must reply `PONG { nonce }` promptly.
* The extension sends `PING` every `heartbeatSec` (20 s). If no `PONG` within 10 s → close and
  reconnect.
* The bridge marks a connection dead if no frame at all is received for `3 × heartbeatSec` and closes it
  (fails its jobs with `EXTENSION_DISCONNECTED`).

## 4. Provider availability

`PROVIDERS_UPDATE` (extension → bridge), sent after `WELCOME` and whenever availability changes
(debounced 500 ms):
```json
{
  "type": "PROVIDERS_UPDATE", "ts": 0,
  "providers": [
    {
      "id": "claude",
      "displayName": "Claude",
      "enabled": true,
      "status": "ready",                 // ready | no_tabs | degraded | login_required | captcha | rate_limited | unhealthy | disabled
      "tabs": { "idle": 1, "busy": 0, "total": 1 },
      "canOpenTabs": true,
      "variants": ["default"],
      "configVersion": "2026.10.20-1",
      "overrideVersion": null,
      "netTap": true,
      "historyModes": ["normal"]
    }
  ]
}
```
Routable statuses: `ready`, `no_tabs` (if `canOpenTabs`), `degraded`. Not routable: everything else.

## 5. Jobs

### 5.1 `JOB_START` (bridge → extension)

```json
{
  "type": "JOB_START", "ts": 0,
  "jobId": "job_01JAZ…",
  "provider": "claude",
  "modelVariant": "default",
  "promptText": "…exact text to type into the composer…",
  "target": { "mode": "new" },                      // or {"mode":"continue","threadUrl":"https://claude.ai/chat/…"} or {"mode":"current","tabId":123}
  "historyMode": "normal",                           // or "temporary"
  "stream": true,
  "wantReasoning": false,
  "timeouts": { "queueMs": 60000, "firstTokenMs": 60000, "totalMs": 300000, "stallMs": 90000 }
}
```
Rules:
* `promptText` max length is enforced by the bridge (default 200 000 chars) and again by the provider
  config (`composer.maxChars`).
* The extension must reply with `JOB_ACCEPTED` or `JOB_ERROR` within 2 s.

### 5.2 `JOB_ACCEPTED` (extension → bridge)
```json
{ "type": "JOB_ACCEPTED", "ts": 0, "jobId": "job_…", "queuePosition": 0 }
```
`queuePosition` 0 = will start immediately. The extension may send further `JOB_ACCEPTED` frames with
updated positions while queued (optional).

### 5.3 `JOB_PROGRESS` (extension → bridge)
```json
{ "type": "JOB_PROGRESS", "ts": 0, "jobId": "job_…", "phase": "generating", "tabId": 123, "detail": {} }
```
Phases in order: `queued` → `preparing_tab` → `preflight` → `injecting` → `submitting` →
`waiting_first_token` → `generating` → `finalizing`. The bridge records the phase; it is used to decide
whether a failure happened **before** the prompt was submitted (safe to retry) or after.

### 5.4 `JOB_DELTA` (extension → bridge)
```json
{ "type": "JOB_DELTA", "ts": 0, "jobId": "job_…", "seq": 17, "kind": "text", "text": " more words", "source": "net" }
```
* `seq` starts at 1, increments by 1 per delta for this job (across kinds).
* `kind`: `"text"` or `"reasoning"`.
* The bridge ignores a delta whose `seq` ≤ the last processed `seq` (duplicates after reconnect), and
  buffers out-of-order deltas until the gap is filled (max 2 s; then skip ahead and add warning
  `delta_gap`).
* Concatenation of all `text` deltas **should** equal `JOB_DONE.text`. It may not (DOM path
  divergence, `replace` events from net-tap parsers that send snapshots). The final `text` in
  `JOB_DONE` is authoritative. How the bridge handles a mismatch is in `07` §6.2.
* Net-tap `replace` events are converted by the extension into deltas when the new snapshot starts
  with the previously emitted text; otherwise the extension stops emitting text deltas for this job and
  adds warning `stream_divergence` (same policy as the DOM path, `04` §5.9).

### 5.5 `JOB_DONE` (extension → bridge)
```json
{
  "type": "JOB_DONE", "ts": 0, "jobId": "job_…",
  "text": "…full final markdown…",
  "reasoning": null,
  "finishReason": "stop",               // stop | length | content_filter
  "threadUrl": "https://claude.ai/chat/2b1c…",
  "threadId": "2b1c…",
  "tabId": 123,
  "modelLabel": "Claude Sonnet 4.5",    // whatever the UI displayed, or null
  "source": "net",                       // net | dom
  "warnings": [],
  "timings": { "queuedMs": 0, "prepareMs": 820, "firstTokenMs": 1650, "totalMs": 9300 },
  "resolution": { "composer.input": 0, "composer.send": 0, "turns.assistant": 0, "answer.content": 1 }
}
```

### 5.6 `JOB_ERROR` (extension → bridge)
```json
{
  "type": "JOB_ERROR", "ts": 0, "jobId": "job_…",
  "code": "SELECTOR_NOT_FOUND",
  "message": "composer.send not found after 5000 ms",
  "submitted": false,                    // true if the prompt may have been sent to the provider
  "partialText": null,                   // partial answer if any
  "detail": { "key": "composer.send", "phase": "submitting" },
  "healthReportId": "hr_…",              // if a report/snapshot was recorded
  "retryAfterSec": null                  // for RATE_LIMITED if the banner contained a reset time
}
```

### 5.7 `JOB_CANCEL` (bridge → extension) and `JOB_CANCELLED` (extension → bridge)
```json
{ "type": "JOB_CANCEL", "ts": 0, "jobId": "job_…", "reason": "client_disconnected" }
{ "type": "JOB_CANCELLED", "ts": 0, "jobId": "job_…", "partialText": "…", "submitted": true }
```
Reasons: `client_disconnected`, `deadline`, `admin`. The extension always answers `JOB_CANCELLED`
(or `JOB_ERROR` with `CANCEL_FAILED`) within 15 s. A `JOB_CANCEL` for an unknown or finished job is
answered with `JOB_CANCELLED` and `partialText: null` (idempotent).

### 5.8 Terminal frames

Exactly one of `JOB_DONE`, `JOB_ERROR`, `JOB_CANCELLED` ends a job. After it, any frame for that
`jobId` is ignored by the bridge (log at debug level).

### 5.9 Sequence diagrams

**Streaming success**
```
Bridge                    Extension BG                 Worker tab
  │ JOB_START ───────────►│                             │
  │◄──────── JOB_ACCEPTED │                             │
  │◄──── JOB_PROGRESS ... │ (navigate, wait ready)      │
  │                       │ run ───────────────────────►│
  │◄──── JOB_PROGRESS ... │◄──────────────── progress ──│
  │◄──── JOB_DELTA seq=1  │◄──────────────── delta ─────│
  │◄──── JOB_DELTA seq=n  │◄──────────────── delta ─────│
  │◄──── JOB_DONE         │◄──────────────── done ──────│
```

**Client disconnects mid-stream**
```
Bridge                    Extension BG                 Worker tab
  │ (HTTP client gone)    │                             │
  │ JOB_CANCEL ──────────►│ cancel ────────────────────►│ click stop, wait idle
  │◄────── JOB_CANCELLED  │◄──────────────── cancelled ─│
```

**Tab closed by the user mid-job**
```
  │                       │ Port disconnect, tab gone   │ ✕
  │◄──── JOB_ERROR(TAB_LOST, submitted=true, partialText)
```

## 6. Config, health, and snapshot messages

All are request/response with `requestId`.

| Request (direction) | Response | Purpose |
|---|---|---|
| `CONFIG_GET {providerId?}` (B→E) | `CONFIG_STATE {requestId, providers: [{id, configVersion, overrideVersion, effective, bundled, override}]}` | Read effective configs (for admin API / maintainer). |
| `CONFIG_OVERRIDE {override}` (B→E) | `CONFIG_ACK {requestId, providerId, status: "applied"|"rejected", errors: [...], overrideVersion}` | Apply a hot fix (`05` §2.4). |
| `CONFIG_REVERT {providerId, to: "bundled"|"previous"}` (B→E) | `CONFIG_ACK` | Undo. |
| `HEALTH_PROBE {providerId?}` (B→E) | `HEALTH_RESULT {requestId, results: [{providerId, status, checks: {key: {found, tier, count}}, tabId}]}` | Run probes now (`04` §9.1). Never types or sends. |
| `HEALTH_REPORTS_GET {since?}` (B→E) | `HEALTH_REPORTS {requestId, reports: [...]}` | Fetch stored reports. |
| `SNAPSHOT_REQUEST {snapshotId}` or `{providerId, capture: true}` (B→E) | `SNAPSHOT_RESULT {requestId, snapshotId, meta, html}` | Fetch a stored snapshot or capture a fresh one from an idle worker tab. |
| `HEALTH_REPORT {report}` (E→B, unsolicited) | — | Pushed whenever a report is created. |

Timeouts for these requests on the bridge side: 10 s (snapshot capture: 20 s).

## 7. Error codes

Every code, where it originates, HTTP mapping used by the bridge (`07` §7), and whether the bridge
may automatically retry. **Automatic retry is only allowed when `submitted === false`** (the prompt
never reached the provider), at most once, on a different tab if available.

| Code | Origin | HTTP | Auto-retry if not submitted | Meaning |
|---|---|---|---|---|
| `NO_EXTENSION` | bridge | 503 | no | No extension connected. |
| `PROVIDER_UNAVAILABLE` | bridge/ext | 503 | no | Provider unknown, disabled, or not routable. |
| `MODEL_NOT_AVAILABLE` | bridge/ext | 404 | no | Model variant not supported. |
| `NO_CAPACITY` | ext | 503 (+`Retry-After: 5`) | no | Queue timeout. |
| `LOGIN_REQUIRED` | ext | 503 | no | Provider shows logged-out state. User must log in. |
| `CAPTCHA_REQUIRED` | ext | 503 | no | Challenge page. User must solve it. |
| `RATE_LIMITED` | ext | 429 (+`Retry-After` if known) | no | Provider usage limit reached. |
| `SELECTOR_NOT_FOUND` | ext | 502 | yes | A critical selector didn't resolve (maintainer trigger). |
| `SELECTOR_AMBIGUOUS` | ext | 502 | yes | Scoring tie for composer. |
| `SELECTOR_SUSPICIOUS` | ext | 502 | no | A click target matched the destructive-action deny list (`08` §4.3). Never retried. |
| `INPUT_REJECTED` | ext | 502 | yes | All insertion strategies failed verification. |
| `SUBMIT_FAILED` | ext | 502 | yes | Could not verify submission. |
| `PROMPT_TOO_LONG` | bridge/ext | 400 | no | Exceeds limits. |
| `UNSUPPORTED_CONTENT` | bridge | 400 | no | Images/files/etc. not supported yet. |
| `MODEL_SELECT_FAILED` | ext | 502 | yes | Model picker steps failed. |
| `NO_RESPONSE` | ext | 504 | no (submitted=true) | No assistant turn appeared before `firstTokenMs`. |
| `GENERATION_STALLED` | ext | 504 | no | No progress for `stallMs`. |
| `GENERATION_TIMEOUT` | ext/bridge | 504 | no | Exceeded `totalMs`. |
| `PROVIDER_ERROR` | ext | 502 | no | Provider displayed/streamed an error. |
| `PROVIDER_INTERRUPT` | ext | 502 | no | Provider needs a user decision (A/B choice etc.) and policy says fail. |
| `TAB_LOST` | ext | 502 | yes | Worker tab closed. |
| `PAGE_NAVIGATED` | ext | 502 | yes | Tab navigated away mid-job. |
| `CANCEL_FAILED` | ext | — | — | Internal; tab marked dirty. |
| `EXTENSION_RESTARTED` | ext/bridge | 502 | yes | Background restarted / connection replaced mid-job. |
| `EXTENSION_DISCONNECTED` | bridge | 502 | yes | Socket died mid-job. |
| `CONFIG_REJECTED` | ext | 400 (admin API) | — | Override invalid. |
| `UNKNOWN_TYPE` | either | — | — | Unknown frame type. |
| `INTERNAL_ERROR` | either | 500 | no | Bug. Includes stack in `detail` (no prompt content). |

## 8. Versioning rules

* `protocolVersion` is an integer major version. Adding optional fields or new message types the other
  side may ignore does **not** bump it. Removing/renaming fields or changing semantics does.
* Both sides declare `capabilities`; a feature is only used if the peer declared it (e.g. the bridge
  only sends `CONFIG_OVERRIDE` if the extension declared `config_override`).
* Keep a `CHANGELOG` section at the bottom of this file when the protocol changes.
